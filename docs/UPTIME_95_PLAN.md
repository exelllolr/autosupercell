# План обеспечения uptime 95% для AutoSupercell

**Цель:** сервис доступен ≥95% времени в месяц (~36 часов допустимого простоя в месяц).

**Текущий стек:** FastAPI (app) + ARQ worker + Redis + Prometheus, развёрнуты через Docker Compose.

---

## 1. Текущее состояние и риски

| Компонент | Сейчас | Риск для uptime |
|-----------|--------|------------------|
| App | 1 инстанс, `restart: unless-stopped`, HEALTHCHECK | Падение процесса, долгий старт без проверки зависимостей |
| Worker | 1 инстанс, `restart: unless-stopped`, без healthcheck | Падение воркера, зависание задач |
| Redis | 1 инстанс, AOF, без healthcheck | Недоступность Redis = недоступность API и воркера |
| Health | Только `GET /api/v1/health` без проверки Redis | Оркестратор может направлять трафик на «мёртвый» инстанс |
| Зависимости | `depends_on` без условия «healthy» | Worker/App могут стартовать до готовности Redis |

---

## 2. Меры по достижению 95% uptime

### 2.1 Health checks и порядок запуска

**Задачи:**

1. **Redis — добавить HEALTHCHECK в `docker-compose.yml`:**
   - Проверка: `redis-cli ping` → `PONG`.
   - Интервал 10–15 с, timeout 5 с, retries 3, start_period 5 с.

2. **App — разделить liveness и readiness:**
   - **Liveness** (как сейчас): `GET /api/v1/health` — процесс жив.
   - **Readiness**: новый endpoint `GET /api/v1/ready` — проверка Redis (ping). Если Redis недоступен — 503.
   - В Docker HEALTHCHECK использовать `/ready` (readiness), чтобы контейнер не считался healthy без Redis.

3. **Worker — добавить healthcheck (опционально):**
   - Либо скрипт внутри контейнера: процесс arq запущен и откликается (например, проверка процесса).
   - Либо оставить только `restart: unless-stopped` и мониторинг через логи/Prometheus.

4. **Зависимости в docker-compose:**
   - `app`: `depends_on: redis` с условием `condition: service_healthy`.
   - `worker`: `depends_on: app` с условием `condition: service_healthy` (чтобы воркер не стартовал до готовности API и Redis).

**Результат:** контейнеры перезапускаются в правильном порядке, трафик не идёт на инстанс без работающего Redis.

---

### 2.2 Автоматический перезапуск и устойчивость процесса

**Уже есть:**

- `restart: unless-stopped` у всех сервисов.
- HEALTHCHECK у app в Dockerfile.

**Добавить/проверить:**

1. **Параметры uvicorn для стабильности:**
   - Запуск с несколькими workers (например, `--workers 2`) только если приложение stateless и нет глобального состояния в памяти; иначе оставить 1 worker.
   - Таймауты: `--timeout-keep-alive`, `--timeout-graceful-shutdown` (uvicorn 0.20+) для корректного завершения при перезапуске.

2. **Graceful shutdown:**
   - В `app/main.py` в `shutdown_event` по необходимости закрывать пулы (Redis, HTTP-клиенты), чтобы не обрывать активные запросы при перезапуске.

3. **Worker:**
   - ARQ уже переподключается к Redis при обрыве; при падении процесса Docker перезапустит контейнер.

**Результат:** при падении процесса или контейнера он перезапускается без длительного «мёртвого» состояния.

---

### 2.3 Мониторинг и реакция на сбои

**Задачи:**

1. **Prometheus (уже есть):**
   - Убедиться, что `app:8000/metrics` стабильно скрапится (сеть autosupercell-network).
   - Добавить алерты (через Alertmanager или облачный Prometheus):
     - Сервис down (нет успешного scrape).
     - Высокий 5xx rate или отсутствие ответов на /health/ready.

2. **Внешний мониторинг uptime (обязательно для 95%):**
   - Сервис типа UptimeRobot, Better Uptime, Cronitor или свой cron каждые 1–5 минут: `GET https://ваш-домен/api/v1/health` (или `/ready`).
   - При 2–3 неуспешных проверках подряд — уведомление (email/Telegram) и при возможности автоматический перезапуск (например, через API хостинга или скрипт на сервере).

3. **Логи и ротация:**
   - Уже настроены loguru и ротация в `app/main.py`. Убедиться, что каталог `logs/` смонтирован и не забивает диск (retention 7 дней — ок).

**Результат:** сбои обнаруживаются за минуты, есть уведомления и возможность перезапуска.

---

### 2.4 Инфраструктура и хостинг

**Рекомендации:**

1. **Сервер/VM:**
   - Минимум 1 GB RAM для app + worker + Redis; 2 GB комфортнее.
   - Автоматический перезапуск Docker после перезагрузки ОС: `systemctl enable docker` (уже в чеклисте).

2. **Сеть и DNS:**
   - Стабильный DNS и при необходимости резервный IP/домен.
   - Если сервис за nginx/caddy — настроить health check бэкенда на `/api/v1/ready` и таймауты.

3. **Резервное копирование (для быстрого восстановления):**
   - Бэкап тома Redis (`redis-data`) по расписанию (если хранятся важные очереди/сессии).
   - Бэкап `.env`, `proxies.txt` и конфигов — чтобы при падении сервера быстро поднять копию.

**Результат:** после сбоя сервера или сети восстановление укладывается в допустимый простой.

---

### 2.5 Что не обязательно для 95%, но полезно для 99%+

- Несколько реплик app за балансировщиком (нужен shared Redis и stateless API).
- Redis в режиме Sentinel или кластер для отказоустойчивости.
- Отдельный сервер для мониторинга (чтобы при падении основного хоста алерты всё равно доходили).

Для целевых 95% достаточно одного узла с качественными health checks, перезапусками и внешним мониторингом.

## 3. Чеклист внедрения

- [ ] **Redis:** добавить HEALTHCHECK в `docker-compose.yml`.
- [ ] **App:** реализовать `GET /api/v1/ready` с проверкой Redis; при необходимости обновить HEALTHCHECK в Dockerfile на `/ready`.
- [ ] **docker-compose:** для `app` и `worker` задать `depends_on` с `condition: service_healthy` (redis для app, app для worker).
- [ ] **Uvicorn:** проверить/добавить таймауты graceful shutdown в CMD/entrypoint.
- [ ] **Внешний мониторинг:** зарегистрировать endpoint в UptimeRobot (или аналоге), настроить уведомления при падении.
- [ ] **Алерты Prometheus:** при использовании Alertmanager — правила на down и высокий error rate.
- [ ] **Документация:** обновить SERVER_CHECKLIST.md и DEPLOY: упомянуть `/ready`, порядок запуска и рекомендации по мониторингу.

## 4. Оценка достижимости 95%

- **Без плана:** единичные падения app/worker/Redis без быстрого перезапуска и без проверки зависимостей могут давать десятки часов простоя в месяц.
- **С планом:** автоматический перезапуск (Docker + health), готовность только при работающем Redis и внешний мониторинг с уведомлениями позволяют укладываться в ~95% uptime на одном сервере при типичной нагрузке и без каскадных сбоев.

Итог: план сфокусирован на health checks, порядке старта, перезапусках и мониторинге — этого достаточно для целевого 95% uptime.

## 5. Мобильная версия

### 5.1 План архитектуры и разработки

Чтобы добиться бесперебойной работы, систему нужно разбить на 4 независимых блока.

1. **Шаг 1. Перенос в серверное окружение (Изоляция)**  
   Сейчас скрипт работает локально. Нам нужно завернуть его в контейнер, чтобы он мог работать на удаленном сервере 24/7.

   - **Что делаем:** Настраиваем Bare-Metal сервер (сервер без виртуализации, так как эмуляторам нужна видеокарта и прямые ресурсы процессора).
   - **Что это даст:** Скрипт не зависит от вашего компьютера, интернета и спящего режима.

2. **Шаг 2. Система очередей (Защита от потери денег)**  
   Если клиент оплачивает заказ, а в этот момент эмулятор завис — запрос не должен потеряться.

   - **Что делаем:** Поднимаем брокер сообщений (например, RabbitMQ или Redis). Все новые запросы на оплату падают в «корзину». Скрипт берет запрос из корзины. Если оплата прошла — запрос удаляется. Если эмулятор завис — скрипт перезагружается, а запрос возвращается обратно в корзину и ждет следующей попытки.
   - **Что это даст:** Ни один платеж не потеряется из-за технических сбоев.

3. **Шаг 3. Обход антифрода и блокировок (Стабильность логина)**  
   Supercell активно банит подозрительную активность.

   - **Что делаем:** Интегрируем сервис ротации резидентных прокси (IP-адреса реальных людей). Настраиваем подмену отпечатков устройства (Device Fingerprinting), чтобы для серверов игры каждый вход выглядел как вход с нового реального телефона. Прописываем логику обработки слетевших сессий (авто-релогин Supercell ID через почту).
   - **Что это даст:** Снижение риска пермабанов аккаунтов и блокировок по железу.

4. **Шаг 4. Self-healing и мониторинг (Автоматическое лечение)**  
   Система должна чинить себя сама.

   - **Что делаем:** Пишем «наблюдателя» (Watchdog). Он раз в минуту проверяет: жив ли эмулятор? Отвечает ли приложение? Если нет — он жестко перезапускает процесс. Прикручиваем алерты в Telegram: если система лежит дольше 5 минут, в чат летит уведомление.
   - **Что это даст:** Тот самый uptime 95%. Если что-то сломалось, система сама восстановится за 1-2 минуты.
